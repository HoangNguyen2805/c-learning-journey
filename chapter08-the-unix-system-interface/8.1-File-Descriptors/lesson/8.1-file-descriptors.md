# 8.1 - File Descriptors

## Big idea

Chapter 7 used the LIBRARY (FILE*, getc, printf). Chapter 8 drops one level: the **system calls** the library is built on. On UNIX, all I/O — files, keyboard, screen, devices — is done by reading and writing **files**, identified by small non-negative integers: **file descriptors**.

```text
FILE* fp        <- library layer  (buffered, portable)
int fd          <- system layer   (raw, UNIX)
```

---

## The three standard descriptors

When your program starts, the shell has already opened three files:

```text
0 = standard input
1 = standard output
2 = standard error
```

That's WHY redirection works: for `prog < infile > outfile`, the shell simply re-attaches descriptors 0 and 1 to those files before your program runs. Your code reads fd 0 and writes fd 1 regardless.

Descriptor 2 (stderr) survives the redirection — errors still reach the screen.

---

## Everything is a file

Keyboard? A file. Terminal screen? A file. Pipe? A file. This uniformity means ONE pair of operations (read/write on a descriptor) handles all I/O. Peripherals look like files, so the same code talks to any of them.

---

## Descriptors vs FILE*

| | file descriptor | FILE* |
|---|---|---|
| type | int | pointer to struct |
| from | open/creat syscalls | fopen |
| I/O | read/write | getc/putc/fprintf... |
| buffering | none (you manage) | library buffers for you |
| portability | UNIX-flavored | ANSI C everywhere |

The FILE structure (8.5 reveals it!) *contains* a descriptor — the library is a convenience layer on the syscalls.

| Concept | Meaning |
